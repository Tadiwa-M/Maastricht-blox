# 05: Movers and brick models

Spec: CONTRACT 7.1 (models, poses, movers) and CONTRACT 8 (live proxy and client motion rule).

## Brick model format

Things that move (buses, boats, people) are **brick models**: small brick assemblies
rendered as one movable object, never baked into chunks. Files: `contract/models/<name>.json`,
generated by `uv run python -m blox_pipeline.models` (in `pipeline/`).

```jsonc
{ "name": "bus", "version": 1,
  "size": [5, 24, 16],                 // studs along i, j; plates along k
  "pivot": [2.5, 12.0, 0.0],           // model origin in local cells (floats): ground centre
  "forward": "+j",                     // always +j
  "parts": { "wheel_fl": {"pivot": [0.5, 18.5, 1.5]} },
  "bricks": [ {"i": 0, "j": 0, "k": 0, "type": 3, "color": 38, "rot": 0, "part": "wheel_fl"} ] }
```

Brick fields follow the chunk record: local cells, record position = min corner of the
rotated box. `part` is optional, and bricks without one form the body.

| Model | Size (i × j × k) | Bricks | Parts | Generator |
|---|---|---|---|---|
| bus | 5 × 24 × 16 (2.5 × 12 × 3.2 m) | 144 | `wheel_fl/fr/rl/rr` (axle pivots) | `pipeline/src/blox_pipeline/models/bus.py` |
| boat | 7 × 30 × 27 | 190 | none; **pivot on the waterline** (k = 3) | `models/boat.py` |
| character | 4 × 1 × 10 | 9 | `leg_l/leg_r` (hip, k 3), `arm_l/arm_r` (shoulder, k 6) | `models/character.py` |

The character is an original blocky figure built from ordinary bricks (box head, square legs,
straight block arms), deliberately not a toy minifigure.

**Building one** (`models/builder.py: ModelBuilder`). Place special pieces by facing first,
then pour the body around them:

```python
# from models/bus.py
m = ModelBuilder("bus", (W, L, H), (W / 2, L / 2, 0.0))
part = m.part(name, (i + 0.5, j + 0.5, 1.5))                 # a wheel spinning about its i axis
m.place("round_brick_1x1", i, j, 0, "N", "black", part)
m.place("door_1x2x4", W - 1, j, 3, "E", "dark_grey")         # passenger doors face +i (right side)
m.place("window_1x2x2", 0, j, BAND[0], "W", "black")         # left-side windows face -i
m.box(0, W, 0, L, 3, BAND[0], "bus_red")                     # skirt: fills only still-empty cells
```

`models/document.py: check_model` re-validates any file independently (bounds, overlaps,
types, colours).

**Loading:** Python `models/document.py`; C# `Runtime/Data/Models/BrickModel.cs`
(`BrickModel.Parse`); JS `viewer/src/models.js` (`buildModel`). Tests: `tests/test_models.py`,
`dotnet/Blox.Tests/BrickModelTests.cs`, `viewer/test/models.test.mjs`.

## Pose

```
Pose = { position: [x, y, z] Unity metres, yaw: degrees clockwise from north }
```

At yaw 0 the model's +j front points north; at yaw 90, east. One type for every mover:

| Engine | Type | Applying it |
|---|---|---|
| C# | `Blox.Data.Pose` (`Runtime/Data/Motion/Pose.cs`) | `Quaternion.Euler(0, yaw, 0)` (`BrickModelRenderer.ApplyPose`) |
| JS | plain object | `poseToObject(pose, obj)`: `position = (x, y, −z)`, `rotation.y = −yaw` |

## PathMover: path + distance → pose

A path is a polyline in Unity metres. `PathMover` gives the pose at distance `s`:

- **straight segments:** exactly on the path, heading = segment direction;
- **corners** (`turnRadius` r > 0), the "two axles" rule: put a rear point r metres behind
  and a front point r metres ahead on the path. Heading = rear → front, position = their
  midpoint. The heading turns smoothly over 2r metres and the corner is cut slightly, like a
  real vehicle;
- loops wrap `s`; open paths clamp it.

```
      front (s + r)
         *
        /            heading = rear -> front
   pose o            position = midpoint
      /
     *---------*  path corner
  rear (s - r)
```

| Engine | File | Notes |
|---|---|---|
| C# | `Runtime/Data/Motion/PathMover.cs` | optional explicit cumulative distances (live shapes use the proxy's `cumDistM`) |
| JS | `viewer/src/mover.js` | same rule; `update(dt)` advances by `speed * dt` |

Tests: `dotnet/Blox.Tests/PathMoverTests.cs`, `viewer/test/mover.test.mjs`.

## Parts and the walk cycle

Parts rotate about their pivot's **local i axis** (CONTRACT 7.1).

- **Wheels:** angle = distance / radius (radius = wheel pivot height), so they roll without
  slipping. Unity: `PathFollower`; viewer: `WheelSpin`.
- **Walk cycle:** the phase advances with **distance**, not time, so feet never slide. Legs
  swing opposite each other, and each arm opposite its leg. The swing grows with speed and
  fades out when stopping. Unity: `Runtime/Gameplay/Core/WalkCycle.cs`; viewer: `WalkCycle` in
  `mover.js`.
- **Sign:** in Unity, `SetPartPitch(part, deg)` with a positive angle tips the part's top
  forward (a wheel rolling forward), so a limb's *foot* swings back. `CharacterWalker`
  therefore passes the negative of the walk-cycle angle. The contract doesn't fix this sign yet
  (see CONTRACT ISSUES in `docs/STATUS.md`).

## Live bus: GTFS-RT → screen

```
OVapi vehiclePositions.pb ─┐
OVapi tripUpdates.pb ──────┤ proxy (Python)
GTFS static (shapes) ──────┘
  sources/gtfs_rt.py      decode protobuf -> VehicleObs (lat, lon, bearing, trip)
  vehicles.py             WGS84 -> RD -> world metres (geo.py); vehicle id
  matching.py             project onto the trip's shape -> shapeId, distAlongShapeM
                          (searches near the last projection first, prefers segments
                           pointing the travel direction: loops and out-and-back routes)
  service.py / api.py     cache; GET /v1/vehicles, /v1/shapes
        │ HTTP JSON (every 5 s)
        ▼
Unity (Blox.Live)
  Unity/LiveClient.cs     polls; LiveJson parses into DTOs; LiveClock tracks proxy time
  VehicleRegistry.cs      one VehicleTrack per vehicle; shapes as ShapePolyline (a PathMover, r = 6 m)
  VehicleTrack.cs         motion rule: render at now - 60 s, interpolate distAlongShapeM
                          between bracketing reports, extrapolate <= 30 s, catch up at
                          <= 40 m/s (no teleport), snap backward jumps
  LiveClient.SamplePoses  -> VehiclePose per vehicle, once per frame
  VehiclePose.ToPose(y)   -> Blox.Data.Pose
        ▼
BrickModelRenderer.ApplyPose(pose)   (the bus model)
```

**Not wired yet:** no component spawns a `BrickModelRenderer` per live vehicle and feeds it
`SamplePoses()`. Everything up to the pose is written and tested
(`dotnet/Blox.Tests/LiveTests.cs`). The look-test scene's bus is a scripted `PathFollower`
instead.

## Walk mode (Unity)

Press **C** in Play mode to take control of the figure (`Gameplay/Locomotion/CharacterWalker.cs`):

1. **Input → direction:** WASD/arrows, relative to the camera yaw (W = away from the camera,
   diagonals not faster). `Gameplay/Core/CharacterMotion.MoveDirection`.
2. **Step:** try the full step. If it is blocked, slide along x, then along z.
3. **Ground:** `Gameplay/Core/GroundProbe.Find` checks the target grid column from feet + 3
   plates down to feet − 15 plates. It looks for the highest solid top with 9 plates of
   headroom, so kerbs are climbed and walls block. It asks `WorldIndex.IsSolid` through
   `IWorldSource`, so Gameplay doesn't depend on Rendering.
4. **Turn** toward the walking direction the short way, at most 540°/s (`CharacterMotion.TurnToward`).
5. **Animate:** `WalkCycle.Step(distance, dt)` → `SetPartPitch` on the legs and arms.
6. **Camera:** `MapCameraRig.FollowTarget` = the figure; the rig stops using WASD for panning.

Walk 1.4 m/s, run (Shift) 3.2 m/s. The maths is tested in
`unity/Assets/Blox/Editor/PureTests~/LocomotionTests.cs`. Nothing has run in a Unity editor yet.
